# 06 · REVIEW WORKFLOW — кто проверяет, PR, доработки, слияние

Отвечает на вопросы гендиректора: «кто проверяет доработки?», «как закрывать несколько задач одним PR?», «когда я смотрю глазами?».

## 1. Жизненный цикл задачи (напоминание)
```
todo → in_progress → done → review → approved
                  ↘ blocked
```
- `done` — агент сделал код + прогнал тест-план задачи локально.
- `review` — ожидает проверки.
- `approved` — слито в `main` (не-CEO задачи) или подписано CEO (CEO-гейт).

## 2. Кто проверяет (трёхуровневая проверка)
**Уровень 1 — CI (автоматический гейт, обязателен для всех).**
lint + typecheck + бюджеты перф. + существующие Vitest/Playwright. Без зелёного CI merge запрещён. Это отсекает большинство регрессий без участия людей.

**Уровень 2 — Reviewer Agent (другой агент, назначенный через GitHub проверять PR).**
После CI зелёного Reviewer Agent:
1. читает файл задачи («Критерии приёмки», «Тест-план»);
2. прогоняет тест-план;
3. проверяет **соблюдение стека** (нет обходных путей — `02_TECH_STACK.md`);
4. проверяет соответствие продукту (`01_PRODUCT.md`) и конвенциям (`00_CONVENTIONS.md`);
5. ставит `approved` (для не-CEO задач — и мержит в `main`) либо возвращает в `in_progress` с конкретными правками.

> Да, «третьему агенту писать проверь последние обновления» — это и есть роль Reviewer Agent. Но не ad-hoc, а как постоянный этап: каждый PR проходит через Reviewer Agent. CEO может в любой момент делегировать spot-чек любому агенту («проверь ветку phase/4»), но каноничный путь — Reviewer Agent + CI.

**Уровень 3 — CEO (только для CEO-гейтов 🔴).**
Задачи с `CEO-гейт: да` (`04_STATUS_LOG.md`, колонка «Гейт») **не мержатся без визуальной приёмки гендиректором**.
Reviewer Agent доводит до `review`, ставит метку «ожидает CEO», и CEO скачивает проект, смотрит глазами (не тестирует!), и либо подписывает `approved`+мерж, либо возвращает правку.
Список CEO-гейтов: см. `ceo/INTERVENTION_POINTS.md`.

## 3. Одним PR закрываем несколько задач
Поддерживается и рекомендуется для подряд идущих задач.
- Когда агент закончил задачу, CEO (или сам агент по плану) говорит «выполняй следующую по плану» → агент берёт следующую `todo` в том же треке/фазе и продолжает в той же ветке.
- Ветка может быть групповой: `phase/4` или `task/T040` (если одна), либо `batch/arena-loop`.
- Заголовок PR: `Closes T040, T041, T042, T043 — Arena loop`.
- В теле PR — чек-лист по каждой задаче (что сделано, как проверить).
- Статусы всех вошедших задач обновляются синхронно в `04_STATUS_LOG.md`.

## 4. Как применять доработки (feedback → задача)
Доработки не теряются и не висят в воздухе:
1. **Мелкая правка в рамках задачи** — комментарий в PR; агент (тот же или новый) правит в той же ветке; Reviewer Agent перепроверяет.
2. **Существенная доработка уже `approved` задачи** — создаётся **новая задача** в `tasks/` с суффиксом, напр. `T040b_ui-polish.md`, с `deps: [T040]` и ссылкой на PR-обсуждение. Она проходит тот же протокол (`05_AGENT_PROTOCOL.md`). Так история сохраняется, и любой агент видит цепочку.
3. **CEO-замечание «не то, что хотел»** — оформляется как новая задача (или возврат `approved→in_progress` с правкой), чтобы статус не врал.

Правило: статус всегда отражает правду. Если передумали — не переписывай `approved` в `done` молча; делай follow-up задачу.

## 5. Модель слияния (кто мержит)
- **Не-CEO задачи:** мержит Reviewer Agent после `approved` (автономия — система работает без человека).
- **CEO-гейт задачи:** мержит CEO после визуальной приёмки.
- **Конфликты веток:** разрешаются в PR (rebase/merge в `main`); статус-лог не переписывается чужими руками без координации.

## 6. Передача между агентами (без потери контекста)
- Каждый агент оставляет в «Лог статуса» файла задачи: что сделал, что `blocked`, как проверить, риски.
- `04_STATUS_LOG.md` — единый индикатор: новый агент по ссылке сразу видит, на какой стадии проект.
- `blocked` задачу новый агент начинает заново (прошлый результат не считается завершённым) — см. `05_AGENT_PROTOCOL.md` §4.

## 7. Шаблон комментария CEO при выдаче
См. `ceo/HANDOFF_TEMPLATE.md`. Коротко: «Ссылка на репо + ссылка на `tracks/<track>.md` (или конкретные T###) + „начни со следующей todo“».
