# 00 · CONVENTIONS — репозиторий, нейминг, PR, код-правила

Обязательно для всех агентов. Нарушение конвенций — повод вернуть PR.

## 1. Структура репозитория
```
/                       корень репо
  client/               игра (Phaser 4 + TS + Vite)
  server/               бэкенд (Fastify + SQLite + Drizzle + Zod + WS)
  admin/         админ-панель и CRM (внутри бэкенда, позже)
  shared/         общие схемы/типы/токены/движок сценариев (используют client и server)
  github_project/       ЭТА папка (инструкции + статус + задачи)
  package.json          workspace-корень
```
- Каждый пакет (`client`, `server`, `admin`, `shared`) — самостоятельный, с собственным `package.json` и `tsconfig`, наследующим базовый.
- Монорепо через pnpm/npm workspaces. Общий `tsconfig.base.json` (strict).

## 2. Нейминг
- **Ветки:** `task/T###` для одной задачи или `phase/N` для группы подряд идущих задач.
  Пример: `task/T040`, `phase/4`.
- **Коммиты:** префикс задачи + глагол: `T040 arena scene scaffold`, `T012 topbar rexUI`.
- **PR:** заголовок «Closes T040, T041, T042 — <кратко>»; тело по шаблону (см. §5).
- **Файлы задач:** `tasks/T###_<slug>.md` (slug — латиница, генерится скриптом).
- **Ассеты:** по `signal-arena-assets-spec.md` §4.5/§7.5, напр. `assets/entities/fake-breakout-phantom/thumb.webp`, `assets/icons/i-arena.svg`.

## 3. Код-правила
- **TypeScript strict** везде; запрет `any` в доменных схемах (`shared/`).
- **Игровой UI — только Phaser/rexUI/Graphics.** Никакого React в клиенте. Zustand — без React-биндингов.
- **Цвет — не единственный носитель статуса** (UI-спец §9/§13): дублируй смысл формой/текстом/иконкой.
- **Нет хардкода строк в коде** — только через copy-keys (`i18n`, `T122`).
- **Нет хардкода HEX** в сценах — только через дизайн-токены (`T002`).
- **Иконки:** SVG (≤400Б после SVGO, core-атлас ≤12КБ), tint по токену. Запрет: emoji/icon-font как prod-иконки, PNG для обычного UI.
- **Ассеты:** растр (webp) лениво по pack; hero-art не в первом сценарии; иллюстрации не блокируют старт.
- **Тесты:** Vitest для юнитов/логики, Playwright для e2e/UI-матрицы. CI зелёный обязателен для merge.

## 4. Definition of Done (на задачу)
Задача `done`, когда:
1. Реализован функционал по «Цель» и «Критерии приёмки» файла задачи.
2. Пройден тест-план задачи (локально).
3. Нет regressions по CI (lint, typecheck, бюджеты, существующие e2e).
4. Статус обновлён в `04_STATUS_LOG.md` и в файле задачи.
5. Открыт PR по шаблону; в описании — как проверить вручную.

## 5. Шаблон PR
```
## Задачи
Closes T###, T###  (можно несколько подряд идущих)

## Что сделано
- ...

## Как проверить
- npm run dev (client) → ...
- playwright run arena

## Статус стека
- [ ] Все компоненты ТЗ использованы как указано (нет обходных путей)
- [ ] Если стек недоступен — задача помечена blocked, обход НЕ искался

## Риски / блоки
- ...
```

## 6. Статус-машина (едина для всех)
`todo → in_progress → done → review → approved`; из `in_progress` также `→ blocked`.
- `blocked`: стек недоступен / зависимость не готова. Без обходного пути. Другой агент позже берёт секцию заново.
- `done`: код + тест-план задачи зелёные локально.
- `review`: ждёт reviewer-agent (не-CEO задачи) или CEO (CEO-гейт).
- `approved`: слито в `main` / подписано CEO.

## 7. Конфликты и передача
- Если задача `in_progress` долго (≥ условлено в PR), CEO может перераспределить: прошлый агент фиксирует что сделал, новый продолжает/начинает секцию заново. Не доделанное = не `done`.
- Никто не переписывает чужие строки в `04_STATUS_LOG.md` без координации в PR/issue.
