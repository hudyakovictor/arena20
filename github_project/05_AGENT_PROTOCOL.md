# 05 · AGENT PROTOCOL

Цель протокола — позволить агенту начать работу по одной ссылке без чтения всех 100+ файлов и без ручной синхронизации статусов.

## 1. Вход

1. В корне прочитай `AGENTS.md`.
2. Запусти `python3 github_project/_meta/generate.py check`.
3. Если пользователь назначил `T###` или трек — следуй назначению. Иначе выбери первую `todo`-задачу, все зависимости которой имеют статус `approved`.
4. Прочитай карточку задачи, затем только релевантные первоисточники из `source/`.

Не изучай все архивы и все фазы перед небольшой задачей: это расходует контекст и повышает риск смешения требований.

## 2. Claim до изменения кода

Используй стабильный идентификатор агента:

```bash
python3 github_project/_meta/generate.py set-status T040 in_progress \
  --agent agent-frontend-01 --note "claim: ArenaScene shell"
```

Команда атомарно обновляет `_meta/tasks.json`, лог задачи, общий статус и треки. Ручное редактирование generated Markdown запрещено.

Если claim отклонён из-за зависимостей или чужого `in_progress`, не обходи проверку. Выбери доступную задачу либо зафиксируй конфликт в issue.

## 3. План задачи

Перед кодом сформулируй для себя:
- что входит и не входит в scope;
- какие файлы/контракты затронуты;
- какие acceptance criteria проверяются автоматически и вручную;
- какой минимальный вертикальный результат можно завершить одним PR.

Не добавляй новые библиотеки и архитектурные слои без необходимости текущей задачи.

## 4. Исполнение

- Работай по `00_CONVENTIONS.md`, `02_TECH_STACK.md` и карточке задачи.
- Проверяй предположения по `source/`, а не по памяти.
- Делай малые проверяемые изменения.
- Новые дефекты вне scope записывай как follow-up; не расширяй текущую задачу скрытно.
- Строки интерфейса — через i18n keys, цвета — через semantic tokens.
- Отсутствующий необязательный арт — `placeholder: true`; отсутствие критической технологии — не повод незаметно сменить стек.

### Когда ставить `blocked`

Сначала собери доказательство: команда, версия, ошибка, минимальный воспроизводимый пример и влияние на acceptance criteria. Затем:

```bash
python3 github_project/_meta/generate.py set-status T040 blocked \
  --agent agent-frontend-01 --note "pnpm ...: точная ошибка; блокирует критерий ..."
```

Проблема сети, прав доступа или локального окружения не доказывает несовместимость технологии. Не коммить временную подмену как production-решение.

## 5. Проверка и завершение

1. Запусти тест-план карточки фактически.
2. Запусти доступные общие проверки: lint, typecheck, unit/e2e по затронутому scope.
3. Зафиксируй конкретные команды и результаты:

```bash
python3 github_project/_meta/generate.py set-status T040 done \
  --agent agent-frontend-01 --note "pnpm typecheck; pnpm vitest ... — ok"
```

`done` означает «реализовано и локально проверено», а не «код написан». После открытия PR переведи в `review`. `approved` выставляет reviewer/CEO после merge или визуального CEO-гейта.

## 6. PR и отчёт

PR должен содержать:
- `Closes T###`;
- краткое описание результата;
- команды проверки и их фактический исход;
- ручную проверку, если нужна;
- риски/блоки;
- подтверждение отсутствия молчаливой подмены стека.

В отчёте пользователю: результат, проверки, оставшиеся риски. Не пересказывай всю историю выполнения.

## 7. Статус-машина

```text
todo → in_progress → done → review → approved
         ↘ blocked → in_progress
review → in_progress  (правки)
```

Административный `--force` допустим только для исправления реестра и требует объяснения в `--note`.
